## Why simply accepting `nlink > 1` is insufficient

A hardlink has no target path that can be containment-checked like a symlink. Another pathname, potentially outside the isolated provider tree, refers to the same inode. A concurrent write through that alias could change bytes during candidate freeze. Therefore the source hardlink must never be adopted as-is.

The safe operation is a verified byte normalization into a new private inode:

1. Accept hardlinked input only at the two locations generated by the pinned writer:
   - `.vercel/output/static/**`
   - `.vercel/output/functions/*.prerender-fallback[.<extension>]`
2. Require a current-user-owned regular source file and a contained pathname.
3. Open with `O_RDONLY | O_NOFOLLOW | O_CLOEXEC`.
4. Bind the copy to the open file description and record `dev`, `ino`, owner, mode, `nlink`, size, `mtimeNs`, and `ctimeNs` before reading.
5. Read from the descriptor using positional reads, verify unchanged metadata, write a new `O_EXCL | O_NOFOLLOW` destination at mode `0600`, and `fsync` it.
6. Read the same source descriptor a second time, require both SHA-256 values to match, then require final descriptor metadata and pathname `lstat` identity to equal the initial values.
7. Require destination owner=current user, mode `0600`, `nlink=1`, no symlink, identical SHA-256, and containment in a `0700` private candidate root.
8. Reject all other hardlink paths, path collisions, environment payload names, credential-like names, special files, symlink escapes, absolute symlinks, or any metadata/content race.

Breaking the inode relationship does not change Vercel provider upload semantics because the provider manifest identifies regular file content, path, and executable state, not local inode identity. The candidate manifest must nevertheless be regenerated after normalization and used as the only adopted boundary.
